# Sunny Narrator Dictionary Hub — прототип v1

> Площадка для обмена файлами словарей (`.dic`), которые являются побочным
> результатом работы нейропереводчика [sunny-narrator](./CLAUDE.md):
> пользователи переводят книги, получают глоссарий терминов/персонажей и
> публикуют его, чтобы другие могли переиспользовать при переводе той же
> книги или серии на тот же языковой пакет.

Документ состоит из двух частей:
1. **Анализ** — модель данных, сценарии, стек, допущения (разделы 1–11).
2. **Промт** — готовый к использованию бриф для генерации первой версии
   кода (раздел 12), собранный по итогам анализа.

---

## 1. Контекст и цель

Формат словаря уже задан кодовой базой sunny-narrator и не проектируется
заново — он импортируется как есть (`src/vocabulary_manager.py:validate_dictionary`):

```
# comment line
Source Term = Target Term, CATEGORY, gender, notes
```

- CSV-подобный текстовый файл, кодировка `utf-8-sig`.
- Строки с `#` — комментарии, игнорируются.
- Обязательная часть: `source = target`. `category` (PERSON/ORG/LOC/…),
  `gender` (he/she/it), `notes` — опциональны.
- Дубли `source` (без учёта регистра) считаются ошибкой.

Площадка не переводит и не редактирует эти файлы — она их **каталогизирует,
валидирует по формату и раздаёт по срезам** (языковая пара, автор книги,
автор словаря, серия/книга).

Языковые коды берутся из того же словаря, что уже используется в проекте
(`src/config.py:lang_code_map`), чтобы не изобретать свой список:
`ru, en, fr, de, es, it, zh, ja, nl, pt, pl, uk, ca, da, fi, sv, nb, ko, ro,
el, lt, mk, hr, sl`. Хранить языковую пару стоит именно этими кодами
(`source_lang`, `target_lang`), а не человекочитаемым названием — это и есть
ключ среза из требования №1.

## 2. Модель данных

Три сущности плюс аутентификация. Данные — файловые (раздел 7), но модель
всё равно нужно зафиксировать как схему, иначе фильтрация развалится.

### 2.1 `Book` — книга (нормализованная, для фильтров/автокомплита)

Отдельная сущность, а не свободный текст в каждом словаре — так «автор
книги» и «серия» становятся управляемыми осями фильтрации с автокомплитом,
а не россыпью разных написаний одного имени.

| поле | тип | описание |
|---|---|---|
| `id` | uuid | |
| `title` | string | название книги |
| `author` | string | автор книги (свободный текст, не обязан быть юзером сайта) |
| `series_name` | string? | название серии, если есть |
| `series_index` | int? | номер книги в серии |
| `created_at` | datetime | |

При загрузке словаря пользователь либо выбирает существующую `Book` из
автокомплита (по `title`+`author`), либо создаёт новую inline. Это решает
пункт требований «серия книг или отдельные книги» — серия не отдельная
сущность верхнего уровня, а необязательное поле на книге; «отдельная книга»
— это просто `Book` с `series_name = null`.

### 2.2 `DictionaryFile` — словарь (основная сущность выдачи)

| поле | тип | описание |
|---|---|---|
| `id` | uuid | |
| `book_id` | uuid → Book | |
| `uploader_id` | uuid → User | «автор словаря» = кто загрузил |
| `source_lang` | code | напр. `en` |
| `target_lang` | code | напр. `ru` |
| `original_filename` | string | |
| `storage_path` | string | путь на диске, не путать с публичным именем |
| `file_size_bytes` | int | |
| `entries_count` | int | посчитано при валидации, для отображения |
| `description` | string? | заметки автора словаря |
| `downloads_count` | int | |
| `status` | enum | `pending` \| `approved` \| `rejected` (см. §10) |
| `uploaded_at` | datetime | |

Индексы среза: `(source_lang, target_lang)`, `book_id` (→ автор книги,
серия — через join), `uploader_id` (→ автор словаря).

### 2.3 `User`

| поле | тип |
|---|---|
| `id` | uuid |
| `email` | string, unique |
| `login` | string, unique |
| `password_hash` | string (argon2id) |
| `email_verified_at` | datetime? |
| `created_at` | datetime |

### 2.4 `EmailVerification`

| поле | тип |
|---|---|
| `user_id` | uuid |
| `code_hash` | string (код не хранится в открытом виде) |
| `purpose` | enum: `register` \| `login` \| `reset` |
| `expires_at` | datetime (TTL ~15 мин) |
| `attempts` | int (лимит попыток ввода, напр. 5) |

## 3. Ключевые сценарии

1. **Анонимный поиск/скачивание.** Просмотр и скачивание словарей не требуют
   регистрации — иначе площадка теряет смысл обмена. Регистрация нужна
   только для **загрузки**.
2. **Загрузка.** Залогиненный пользователь выбирает файл → выбирает/создаёт
   `Book` → указывает `source_lang`/`target_lang` → сервер валидирует формат
   и размер → файл сохраняется, запись создаётся.
3. **Регистрация.** login + email + пароль → код на email → ввод кода →
   аккаунт активен.
4. **Фильтрация.** `source_lang` + `target_lang` (оба или один), `author`,
   `uploader`, `series_name`, `book_id`, полнотекстовый поиск по названию
   книги — комбинируются через AND.

## 4. Фильтрация и срезы данных

Обязательные срезы из требований:
- по `source_lang`/`target_lang` (мультиязычность, п.1);
- по автору книги, автору словаря, языкам, серии/книге (п.2).

Эндпоинт выдачи — один список с query-параметрами (см. §8), а не отдельные
эндпоинты на каждый срез: это самая дешёвая реализация на файловом
хранилище и покрывает комбинации фильтров без роста числа маршрутов.

## 5. Загрузка файлов — валидация

Жёсткая проверка в два этапа, оба обязательны:

1. **Формообразующая** (до чтения содержимого):
   - расширение из белого списка: `.dic` (плюс `.txt` как алиас, если
     проект решит разрешить — уточнить у пользователя, см. §11);
   - `Content-Type` заявленный клиентом игнорируется как источник истины,
     проверяется реальными байтами (сигнатура текстового файла, отсутствие
     нулевых байт → не бинарник);
   - размер: см. допущение по лимитам в §11 — до подтверждения от
     пользователя реализовать как **два конфигурируемых порога**
     (`MIN_FILE_SIZE_BYTES`, `MAX_FILE_SIZE_BYTES`), не как захардкоженные
     числа, чтобы правку не пришлось искать по коду.
2. **Содержательная**: файл целиком читается и валидируется по той же
   грамматике, что и `validate_dictionary()` в sunny-narrator (`source =
   target[, category, gender, notes]`, `#`-комментарии, без дублей
   `source`). Не проходит — сервер отвечает списком ошибок построчно, файл
   не сохраняется. Это переиспользование бизнес-правила, а не его
   переизобретение — при желании функцию можно буквально скопировать/
   портировать один в один.

## 6. Регистрация и подтверждение по коду

Провайдер отправки email — по аналогии с тем, как в sunny-narrator уже
разведены независимые LLM-провайдеры через `.env` (`src/config.py`),
здесь стоит сделать то же самое: **один общий интерфейс `EmailSender`,
две реализации** (`Resend`, `SMTP2GO`), выбор через `.env`
(`EMAIL_PROVIDER=resend|smtp2go` + соответствующий API-ключ). Рекомендация
по умолчанию — **Resend** (проще REST API, щедрый free tier), SMTP2GO —
как fallback/альтернатива без переписывания кода.

Поток:
1. `POST /auth/register` (login, email, password) → создаётся `User` с
   `email_verified_at = null`, создаётся `EmailVerification(purpose=register)`,
   код (6 цифр) отправляется на email.
2. `POST /auth/verify` (email, code) → сверка хэша кода, проверка TTL и
   лимита попыток → `email_verified_at = now()`.
3. Логин выдаёт сессионную куку или JWT — выбор не принципиален для v1,
   но куку проще защитить от XSS (`HttpOnly`, `Secure`, `SameSite=Lax`).

## 7. Технологический стек и хранение данных

**Рекомендация: Python + FastAPI + SQLite.**

- Python — тот же язык, что и основной проект sunny-narrator, меньше
  контекстного переключения для сопровождения.
- FastAPI даёт декларативную валидацию (Pydantic) «из коробки» — прямое
  попадание в требование о жёсткой проверке форматов.
- SQLite — это **тоже файл** (`data/app.db`), а не отдельный
  сервис/процесс: удовлетворяет требованию «хранение данных в файлах» и
  при этом даёт индексы и нормальные `WHERE`-фильтры вместо ручного
  сканирования JSON на каждый запрос. Один файл = тривиальный бэкап
  (`cp app.db app.db.bak`).
- Сами `.dic`-файлы — на диске рядом, не в БД:
  `data/uploads/{dictionary_id}/{original_filename}`, в SQLite — только
  метаданные и путь.
- Node.js (Express/Fastify + `better-sqlite3`) — равноценная альтернатива
  с теми же характеристиками; выбор между ними не меняет архитектуру
  документа, только синтаксис реализации.

Если на файловом хранении настаивают буквально (без SQLite) — деградация:
один `data/index.json` как «таблица» `DictionaryFile`+`Book`, чтение целиком
в память при старте процесса, перезапись атомарно (`os.replace`) при
каждой мутации. Годится, пока каталог небольшой (тысячи записей); поиск
по фильтрам — линейным проходом по списку в памяти. Обозначено как
**вариант Б** на случай, если SQLite сочтут избыточным.

## 8. API (черновой набросок)

```
GET  /api/dictionaries
     ?source_lang=&target_lang=&author=&uploader=&series_name=&book_id=&q=&page=
GET  /api/dictionaries/{id}
GET  /api/dictionaries/{id}/download
POST /api/dictionaries              (multipart, auth required)

GET  /api/books?q=                  (автокомплит при загрузке)
POST /api/books                     (создание inline при загрузке)

POST /api/auth/register
POST /api/auth/verify
POST /api/auth/login
POST /api/auth/logout
```

## 9. Требования к серверу

Цель — минимум: 1 vCPU / 512 МБ–1 ГБ RAM, Ubuntu LTS, без отдельного
процесса БД (SQLite встроен), без Redis/очередей на v1 (email отправляется
синхронно в запросе — при таймауте провайдера это не страшно на масштабе
регистраций одного нишевого сайта). Обратный прокси — Caddy или Nginx
перед приложением для TLS и раздачи статики.

## 10. Вне рамок v1 (out of scope)

- Модерация загруженных словарей (в модели заложено поле `status`, но
  ручной/автоматической проверки на v1 нет — все загрузки сразу
  `approved`; поле остаётся заделом на будущее).
- Рейтинги/комментарии/версионирование словарей одной книги.
- Программный API-токен для автопубликации прямо из sunny-narrator CLI
  после перевода — естественное развитие, но не в первой версии.
- Восстановление пароля (`purpose=reset` в модели заложен, поток — нет).

## 11. Открытые вопросы / допущения — **требуют подтверждения перед стартом кода**

1. **Лимиты размера файла.** В требовании оба числа сформулированы как
   «не более»: «не более 1 мегабайта, не более 32 мегабайт» — это
   взаимоисключимо как два верхних порога одного и того же файла.
   Принятое здесь допущение: **1 МБ — не более чем ожидание описания к нему , 32 МБ — жёсткий верхний
   потолок размера файла**. Если имелось в виду что-то другое (например,
   1 МБ — лимит на превью, 32 МБ — на архив из нескольких словарей), нужно
   поправить §5 и модель.
2. **Разрешённые расширения.** Взят только `.dic`. Нужно ли также принимать
   `.csv`/`.txt` с тем же содержимым (в проекте `.dic` — по сути CSV)?
3. **Логин vs email при входе.** Регистрация — по login **и** email;
   вход — по обоим или только по одному из них?
4. **Модерация на v1.** Подтверждено ли, что загрузки публикуются сразу
   без ревью (см. §10), или нужен режим «на проверке» с первого дня?

```
Построй веб-приложение "Sunny Narrator Dictionary Hub" — каталог файлов

ФОРМАТ СЛОВАРЯ (валидируй именно так, не придумывай свой парсер):
текстовый файл в utf-8-sig, построчно:
  - строки, начинающиеся с "#" — комментарии, пропускаются;

3. User(id, email unique, login unique, password_hash [argon2id],
   email_verified_at?, created_at).
4. EmailVerification(user_id, code_hash, purpose['register'|'login'|'reset'],
   expires_at, attempts) — код 6 цифр, TTL 15 минут, максимум 5 попыток
   ввода, затем код инвалидируется.

ЯЗЫКОВЫЕ КОДЫ (source_lang/target_lang, ISO-подобные, фиксированный список):
ru, en, fr, de, es, it, zh, ja, nl, pt, pl, uk, ca, da, fi, sv, nb, ko, ro,
el, lt, mk, hr, sl.

API:

            подставь финальные значения из §11 перед реализацией), файл не

  GET  /api/books?q= — автокомплит по title/author.
  POST /api/books — создание книги inline.
  POST /api/auth/register {login, email, password}
  POST /api/auth/verify   {email, code}
  POST /api/auth/login    {login_or_email, password}

Требование к ресурсам: приложение должно работать на Ubuntu-сервере
1 vCPU / 512 МБ–1 ГБ RAM без отдельного процесса БД или очереди — весь
```
